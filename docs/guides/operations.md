# Operations guide (Phase 9.11)

Single-region deployment on AWS Seoul with a Cloudflare edge (ADR-0007, prd §12). Names follow
`powehi-<env>` where `<env>` is `staging` or `prod`: ECS cluster `powehi-<env>-cluster`, service
`powehi-<env>-service`, RDS instance `powehi-<env>-db`.

Status: written ahead of the first production apply. Commands marked **unrun** have not been
exercised against a live account (owner prerequisites: issue #118). The restore drill below must
be run once and its measurements recorded in prd §12.7 before the 9.11 box flips.

## Deploy

Releases are tagged `vX.Y.Z` on `main`; `release.yml` builds and cosign-signs the image and
`deploy.yml` rolls staging, smoke-tests, then waits for the `production` approval. Details and
the failure modes: `docs/runbooks/server-deploy.md`. Infrastructure changes go through
`infra-apply.yml` (staging auto-applies on merge; prod only via the `production` approval).

## Rollback

Server: re-run **Deploy — server to ECS** from `main` with the previous image digest
(`docs/runbooks/server-deploy.md`, "Rollback"). The database is never rolled back by a deploy;
migrations are forward-only, so only roll back to a release compatible with the current schema.

Infrastructure: revert the PR that changed `infra/` and let `infra-apply.yml` apply it. Never
edit resources in the console; the next apply would undo it or fight it.

## Restore (RDS)

RDS keeps 7 days of automated backups and point-in-time recovery (`modules/data`,
`backup_retention_period = 7`). Prod has deletion protection and writes a final snapshot
`powehi-prod-db-final` on deletion. Restoring never overwrites the running instance: restore
into a new, temporary instance, check it, then cut over or discard.

1. Pick the source: latest automated snapshot, or a PITR time (UTC) before the incident.
   ```sh
   aws rds describe-db-snapshots --db-instance-identifier powehi-prod-db \
     --snapshot-type automated --query 'DBSnapshots[].[DBSnapshotIdentifier,SnapshotCreateTime]'
   aws rds describe-db-instances --db-instance-identifier powehi-prod-db \
     --query 'DBInstances[0].LatestRestorableTime'
   ```
2. Restore to a temporary instance. It must use the data module's DB subnet group and a security
   group that admits only the task security group (or a one-off task for the check), and it must
   stay `--no-publicly-accessible`:
   ```sh
   aws rds restore-db-instance-to-point-in-time \
     --source-db-instance-identifier powehi-prod-db \
     --target-db-instance-identifier powehi-restore-drill \
     --restore-time <UTC-timestamp> \
     --db-subnet-group-name <data module subnet group> \
     --vpc-security-group-ids <db security group> \
     --no-publicly-accessible --no-multi-az
   aws rds wait db-instance-available --db-instance-identifier powehi-restore-drill
   ```
   (**unrun**; for a snapshot use `restore-db-instance-from-db-snapshot`.) A restored instance
   gets its own RDS-managed master secret only if `--manage-master-user-password` is passed;
   otherwise reuse the source credentials through a task, never copy them to a workstation.
3. Verify without exposing data: point a staging task (not prod) at the restored instance via
   a throwaway task definition, run the deployed smoke test, and check the migration table row
   count matches. Do not query message or KeyPackage tables by hand: they hold ciphertext and
   metadata only, but the zero-knowledge posture is that nobody needs to read them.
4. Cut over (real incident only): update the `database_url` secret to the restored endpoint,
   then force a new deployment of the service (`aws ecs update-service --force-new-deployment`).
   Record the data-loss window (RPO) and total time (RTO) in the incident notes.
5. Delete the drill instance (`--skip-final-snapshot`) and any snapshot you made for it.

Valkey holds only volatile queue state (prd §12.7); no restore is needed, tasks reconnect and
clients re-poll. Mailbox data lives in Postgres; media objects live in R2.

## Secret rotation

All server secrets live in Secrets Manager under `powehi/<env>/` and are read by the task at
start. After changing any value, force a new deployment so tasks pick it up.

| Secret | How to rotate |
|---|---|
| RDS master password | RDS-managed (`manage_master_user_password`); rotate with `aws secretsmanager rotate-secret --secret-id <db_master_secret_arn>`. |
| `database_url`, `redis_url` | `database_url` uses the dedicated `powehi_app` role (below), not the master. Rebuild from the rotated credentials, `put-secret-value`, redeploy. |
| Valkey AUTH token | Generated by `modules/data` (write-only, version 1). Bump `secret_string_wo_version` and apply, update the ElastiCache auth token, update `redis_url`, redeploy. **unrun** |
| `handle_oracle_secret_token` | Generate a new random value, `put-secret-value`, redeploy. Existing handle hashes depend on it: check the server docs before rotating a live environment. |
| `vapid_private_key_pem` | Rotating invalidates every browser push subscription; treat as a breaking change. |
| R2 access key | Re-apply `modules/edge` with the token recreated, update `r2_access_key_id` / `r2_secret_access_key`, redeploy. |

### Dedicated database role (issue #243)

The RDS master password rotates; the static `database_url` secret must never carry it. Create an
application role once per environment, from a one-off task or SSM session inside the VPC (the
database is not publicly reachable), connected as the master user. The server runs migrations at
startup, so the role owns the schema; it is not a superuser and has no `CREATEROLE`/`CREATEDB`.
**unrun** (needs a deployed database).

```sql
-- psql -v pw="$(cat)" on stdin; never put the password on a command line
CREATE ROLE powehi_app LOGIN PASSWORD :'pw' NOSUPERUSER NOCREATEDB NOCREATEROLE;
GRANT CONNECT ON DATABASE powehi TO powehi_app;
GRANT powehi_app TO CURRENT_USER;            -- RDS: lets the master hand over ownership
ALTER SCHEMA public OWNER TO powehi_app;
REASSIGN OWNED BY CURRENT_USER TO powehi_app; -- only if a prior run created tables as master
```

Then write `postgres://powehi_app:<pw>@<endpoint>:5432/powehi?sslmode=verify-full&sslrootcert=/etc/powehi/rds-global-bundle.pem` to
`powehi/<env>/database_url` (the CA bundle is baked into the image) and force a new deployment.
Rotate `powehi_app` by `ALTER ROLE ... PASSWORD`, `put-secret-value`, redeploy; master rotation no
longer affects the service.

Never paste a secret value into a PR, issue, workflow log or shell history; pass it on stdin
(`--secret-string file:///dev/stdin`) or use the console.

## Tunnel token rotation

`tunnel_token` is the `cloudflared` sidecar's token (`modules/edge`, secret `powehi/<env>/tunnel_token`).
Rotate by replacing the tunnel secret in Cloudflare (dashboard, or recreating the tunnel through
`modules/edge`), writing the new token with `put-secret-value`, then forcing a new deployment.
The service is briefly unreachable while the old sidecar disconnects. **unrun**

## Certificate pin rotation

`docs/runbooks/cli-pin-rotation.md`. Add the new pin and ship a CLI release before the edge
changes issuers; remove the old pin only after releases carrying the new set are the minimum
supported version.

## Cost check

Monthly: AWS Cost Explorer grouped by service, filter on tag `Environment`. The expected
drivers are Fargate (one task per env), RDS single-AZ, ElastiCache, and NAT/data transfer.
A drifted figure usually means a task stuck in a restart loop or a leftover drill instance:
list `aws rds describe-db-instances` and `aws ecs list-tasks` and compare with the modules.
Set an AWS Budget alert for the account if the owner has not (not managed by OpenTofu yet).

## Alarms

Alarms go to the SNS email topic from `modules/monitoring` (running tasks below 1, task stops,
RDS CPU/storage/connections, cache memory). If `alert_email` (CI: secret `STAGING_ALERT_EMAIL`) is unset there are no alarms, and
the subscription must be confirmed from the email once. See ADR-0007 for the metrics choice.
